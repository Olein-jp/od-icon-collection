
# OD Icon Collection
## WordPressプラグイン開発仕様書 v1.0

### 1. プロジェクト概要

WordPress 7.1で導入された公式SVG Icon Registration APIを利用し、複数のオープンソースアイコンライブラリを標準のアイコンブロックで利用可能にする独立プラグインを開発する。

プラグイン名：OD Icon Collection
スラッグ：od-icon-collection
テキストドメイン：od-icon-collection
初期バージョン：1.0.0
最低対応WordPress：7.1
公開先：GitHub（WordPress.orgへの登録は予定しない）
プラグイン本体ライセンス：GPL-2.0-or-later

目的は、アイコンブロックに独自の選択画面を追加することではない。

WordPress標準の「アイコンライブラリ」画面に、ライブラリごとのアイコンコレクションを追加し、標準UIから検索・選択できるようにする。

#### 開発の基本原則

- WordPress標準APIを優先する。
- 独自アイコンブロックは作らない。
- 独自のアイコン選択モーダルは作らない。
- WordPress本体のファイルを変更しない。
- 非公開APIや内部実装への依存を避ける。
- フロントエンドへの不要なJS/CSS追加を行わない。
- エディターの検索・選択・カラー設定などを独自実装で置き換えない。
- 将来のアイコンコレクション追加を容易にする。
- GitHubからインストール可能なZIPを生成する。
- オフライン環境でも同梱アイコンを利用可能にする。

### 2. 実現したいユーザー体験

#### 2.1 アイコン選択画面

WordPress標準のアイコンブロックを挿入し、アイコンライブラリを開く。

画面左側のコレクション一覧に、次のような項目を表示する。

- すべて
- WordPress
- Feathericon
- Font Awesome Free
- Material Symbols

ユーザーが「Feathericon」を選択した場合、右側にFeathericonのアイコン一覧を表示する。

「Font Awesome Free」を選択した場合、Font Awesome Freeのアイコン一覧を表示する。

検索欄にはWordPress標準の検索UIを利用する。

#### 2.2 アイコン選択後

選択したアイコンは標準のcore/iconブロックとして保存する。

ブロックの以下の機能を維持する。

- アイコンの選択・変更
- 色変更
- サイズ変更
- 配置
- 回転・反転
- その他WordPress標準機能

アイコンを変更しても標準ブロックの属性や保存形式を不必要に変更しない。

#### 2.3 ブロックの識別子

各アイコンは次の形式で識別する。

od-feathericon/icon-name
od-fontawesome-free/icon-name
od-material-symbols/icon-name

例：

od-feathericon/home
od-fontawesome-free/house
od-material-symbols/search

同じ名前のアイコンが複数ライブラリに存在しても衝突しないこと。

一度採用した識別子は将来のアップデートでも原則変更しない。

### 3. 対応アイコンライブラリ

初期バージョンでは以下の3種類を実装する。

#### 3.1 Feathericon

コレクションスラッグ：
od-feathericon

表示名：
Feathericon

公式リポジトリ：
https://github.com/feathericon/feathericon

ライセンス：
MIT

注意：
FeathericonとFeather Iconsは別プロジェクトである。
今回の初期実装ではfeathericon/feathericonを使用する。

#### 3.2 Font Awesome Free

コレクションスラッグ：
od-fontawesome-free

表示名：
Font Awesome Free

公式リポジトリ：
https://github.com/FortAwesome/Font-Awesome

ライセンス：
SVGはCC BY 4.0

対象：
Font Awesome Freeで配布が許可されているSVGアイコン。

Pro版や有償ライセンス限定のアイコンは同梱しない。

初期実装ではSolidとRegularを対象にする。
Brandsは商標の扱いを別途確認するため初期実装から除外する。

SolidとRegularに同名アイコンが存在する場合は、
それぞれ別の識別子を使用する。

例：

od-fontawesome-free/solid-heart
od-fontawesome-free/regular-heart

将来の追加や更新でも既存の識別子を維持する。

#### 3.3 Material Symbols

コレクションスラッグ：
od-material-symbols

表示名：
Material Symbols

公式リポジトリ：
https://github.com/google/material-design-icons

公式アイコン一覧：
https://fonts.google.com/icons

ライセンス：
Apache License 2.0

対象：
Material Symbolsの公式配布物。

初期実装ではOutlinedスタイルを優先する。

Rounded、Sharpなどのスタイルは将来的に追加できる構造にする。

バリアントを追加する場合は、識別子が衝突しないようにする。

例：

od-material-symbols/outlined-home
od-material-symbols/rounded-home

フォントファイルをそのままSVGアイコンとして扱わない。

公式配布物から再配布可能なSVGを取得する方法を調査し、必要に応じてオフラインのビルド工程でSVGを生成する。

単なる文字列やフォントグリフの代用ではなく、実体のあるSVGを登録すること。

#### 3.4 将来的な追加

以下の追加を想定する。

- Lucide
- Tabler Icons
- Bootstrap Icons
- その他GPL互換のアイコンライブラリ

新しいコレクションを追加しても、既存の登録処理を大幅に書き換えずに済む構造とする。

### 4. WordPress公式APIの利用

#### 4.1 コレクション登録

以下の公式関数を使用する。

wp_register_icon_collection()

initフックで登録する。

登録するコレクションには必ず以下を指定する。

- スラッグ
- ラベル
- 説明

スラッグにはod-プレフィックスを使用する。

#### 4.2 アイコン登録

以下を使用する。

wp_register_icon()

各アイコンに次の情報を設定する。

- コレクション付きアイコン識別子
- ラベル
- SVGファイルパス

原則としてfile_pathを使用する。

SVGの文字列をPHPコードに大量に直接埋め込まない。

file_pathにはプラグインディレクトリから解決した絶対パスを指定する。

SVGファイルが存在し、読み取り可能であることを事前に検証する。

ファイルが見つからない場合、壊れたアイコンを登録せず、開発時に確認できるエラーを記録する。

#### 4.3 登録順序

必ず以下の順序を守る。

1. 有効なコレクションを判定
2. コレクション登録
3. アイコンメタデータを読み込む
4. SVGファイルの妥当性を確認
5. アイコン登録

コレクション登録に失敗した場合、そのコレクションの個別アイコン登録は実行しない。

#### 4.4 不必要な拡張は禁止

WordPress標準のREST APIとアイコン選択UIを利用する。

独自RESTエンドポイントは初期バージョンでは作らない。

core/iconの保存形式を独自に変更しない。

### 5. SVG互換性と変換処理

このプラグインにおける重要な要件。

WordPress 7.1のSVG Icon APIには許可されるSVG要素・属性の制限がある。

公式ドキュメントに記載された7.1時点の基本的な許可要素は以下。

- svg
- path
- polygon

stroke属性やcircle、line、polylineなどの要素が除去される可能性がある。

したがって、アイコンSVGをそのまま配置するだけではなく、対応性を検証する必要がある。

#### 5.1 SVG変換

ビルド時に次を行う。

1. 元SVGを解析
2. 利用できない要素・属性を検出
3. 必要に応じてパスへ変換
4. カラー指定を正規化
5. viewBoxを保持
6. WordPressのサニタイズ処理を想定した検証
7. 変換前後の見た目を比較
8. 配布用SVGを書き出す

変換はオフラインのビルド工程で実施する。

サイト稼働時やエディター実行時に毎回変換しない。

#### 5.2 線画SVG

strokeを使った線画アイコンの場合、単純にstrokeを削除してはならない。

必要に応じてstrokeを塗りつぶしパスへ変換し、元の線幅、角丸、線端を可能な限り保持する。

単純なSVG最適化だけでは変換できないケースを想定する。

変換不能なSVGは無理に登録せず、除外理由を報告する。

#### 5.3 色の変更

標準アイコンブロックの色変更を利用できること。

原則としてSVG内の塗りつぶし色はcurrentColorを使用する。

WordPress側の許可属性を考慮し、pathやpolygonのfill指定で対応する。

特定のカラーコードを固定しない。

ただし、元のアイコンが複数色を必要とする場合は、仕様に沿って個別検討する。

#### 5.4 変換品質

以下の形状を重点的に検証する。

- 円形
- 直線
- 曲線
- 角丸
- 中抜き
- 複数パス
- 細い線
- 複雑な図形

SVGがエラーなく読み込めるだけでは合格としない。

元SVGと変換後SVGをブラウザで描画し、視覚的な差異を比較する。

Playwrightなどによるスクリーンショット比較を推奨する。

SVG変換の失敗を検出できる仕組みを用意する。

元SVGを勝手に上書きしない。

### 6. アイコンメタデータ

アイコンの登録情報はコレクションごとに管理する。

例：

{
  "collection": "od-feathericon",
  "source_version": "取得したバージョン",
  "icons": [
    {
      "name": "home",
      "label": "Home",
      "file": "home.svg"
    }
  ]
}

nameは登録用の安定した識別子とする。

labelは検索可能な表示名として使用する。

日本語検索は初期要件としない。

WordPress標準の検索APIが持つ機能の範囲で動作させる。

日本語名、別名、キーワード検索は将来の拡張項目とする。

メタデータ生成時には重複、命名規則違反、不正なファイルパス、実体のないSVGを検出する。

### 7. コレクション管理画面

WordPress管理画面に設定ページを用意する。

場所：

設定 → OD Icon Collection

設定画面では、各コレクションの有効・無効を切り替えられるようにする。

初回有効化時は3つのコレクションをすべて有効とする。

表示する情報：

- ライブラリ名
- ライブラリのバージョン
- 登録対象のアイコン数
- 登録成功数
- 登録失敗数
- 有効・無効の切り替え
- 公式リポジトリへのリンク
- ライセンス名とライセンスへのリンク

設定保存にはWordPress Settings APIを優先する。

設定変更権限はmanage_optionsとする。

nonce検証、権限チェック、入力値のホワイトリスト検証を行う。

外部ネットワークへの通信を要求しない。

#### 7.1 無効化時の安全性

コレクションを無効化すると、そのコレクションのアイコンが登録されなくなる。

すでに記事で利用中のアイコンが表示されなくなる可能性がある。

そのため、無効化操作時には警告を表示する。

警告例：

「このコレクションを無効化すると、すでに投稿や固定ページで利用しているアイコンが表示されなくなる場合があります。」

無効化によって投稿本文やブロック属性を削除・変更してはならない。

再び有効化した場合は、保存済みのアイコン識別子から表示を復旧できること。

設定画面では使用中アイコン数の全サイト横断集計を必須としない。

### 8. 拡張性

将来のライブラリ追加に対応できる構造にする。

プラグイン内部ではコレクションのメタデータと登録ロジックを分離する。

外部コードから登録可能なコレクションを追加できるフィルターフックを用意する。

フック名：

od_icon_collection_collections

このフィルターでは、コレクションの定義を追加・変更できるようにする。

各定義に最低限必要な情報：

- slug
- label
- description
- icons_directory
- manifest_path

ただし任意のディレクトリやファイルを無検証で読み込んではならない。

パスの正規化、実在確認、読み取り権限確認、拡張子確認を行う。

登録の失敗によってプラグイン全体が停止しない構造とする。

外部フックから追加されたアイコンにもWordPress標準のSVGサニタイズが適用されること。

### 9. パフォーマンス

数千種類のアイコン登録に対応できること。

特にFont Awesome FreeやMaterial Symbolsを考慮する。

#### 必須方針

- 稼働時にSVGを変換しない。
- SVGファイルの内容を全件PHP文字列として事前展開しない。
- アイコン登録には原則file_pathを使用する。
- 不要なネットワークリクエストを発生させない。
- アイコンライブラリ全体のSVGをフロントエンドへ読み込まない。
- 無効なコレクションは登録対象にしない。
- 同じメタデータを繰り返し解析する処理を避ける。

#### 検証対象

1. WordPress管理画面の通常表示
2. ブロックエディターの起動
3. アイコンライブラリの起動
4. コレクション切り替え
5. アイコン検索
6. アイコン選択
7. フロントエンド表示
8. 保存済みコンテンツの再編集

REST APIが大量のアイコン情報を返す場合のメモリ使用量や応答時間も調査する。

標準APIの挙動に制約がある場合は、独自APIへ置き換える前に実測結果を報告する。

### 10. セキュリティ

外部取得したSVGを無条件に信頼しない。

次の要素を禁止または検出する。

- script
- foreignObject
- イベントハンドラー属性
- 外部リソースへの参照
- 実行可能な埋め込みコード
- 危険なURL
- 不必要なstyle指定

WordPress本体のSVGサニタイズに加えて、ビルド時に検査を実施する。

SVGを安全に解析するライブラリを使用し、XML外部実体参照などの攻撃を許可しない。

設定画面の出力は適切にエスケープする。

ユーザー入力を直接ファイルパスへ連結しない。

ファイルパスのディレクトリトラバーサルを防ぐ。

最低限以下を用意する。

- 適用されるNOTICE

### 13. 動作要件

#### 13.1 プラグイン有効化

WordPress 7.1以上で有効化できること。

対応APIが存在しない環境では致命的エラーを起こさない。

未対応環境であることを管理者へ通知する。

PHPの最低対応バージョンは、対象WordPressと実装依存を確認したうえで決定し、READMEとプラグインヘッダーに明記する。

#### 13.2 登録確認

以下のエンドポイントで登録状態を確認する。

GET /wp-json/wp/v2/icon-collections

GET /wp-json/wp/v2/icons?collection=od-feathericon

GET /wp-json/wp/v2/icons?collection=od-fontawesome-free

GET /wp-json/wp/v2/icons?collection=od-material-symbols

REST APIへのアクセスにはWordPressが要求する認証と権限を使用する。

コレクション数、登録アイコン数、検索結果が一致すること。

#### 13.3 エディター確認

標準アイコンブロックを挿入する。

ライブラリ画面の左側に登録済みコレクションが表示されること。

各コレクションを選択すると該当ライブラリのアイコンだけが表示されること。

検索によって目的のアイコンを絞り込めること。

#### 13.4 保存・公開

アイコンを選択して投稿を保存する。

公開ページで正常に表示されること。

次を確認する。

- SVGが壊れていない
- 色が反映される
- サイズが反映される
- レイアウトが崩れない
- 再編集しても表示される
- 更新後も識別子が維持される

### 14. テスト仕様

#### 14.1 単体テスト

- コレクション登録成功
- 重複登録防止
- 不正スラッグ検出
- アイコン登録成功
- 存在しないSVGの検出
- 不正メタデータの検出
- 無効化設定の反映
- フィルターフック経由の追加
- 不正パスの拒否
- 権限のないユーザーによる設定変更の拒否

#### 14.2 SVGテスト

- 非対応要素の検出
- stroke変換
- viewBox維持
- currentColor対応
- サニタイズ後の描画
- 元SVGとの視覚比較
- 空白SVGの検出
- 外部参照の検出
- 安全性検証

変換前後の比較は代表アイコンだけではなく、変換結果全体を機械的に検査する。

複雑なアイコンは追加の目視確認対象とする。

#### 14.3 統合テスト

Playwright等を利用し、WordPress管理画面で以下を検証する。

1. アイコンブロック挿入
2. アイコンライブラリ起動
3. Feathericon選択
4. アイコン検索
5. アイコン選択
6. 色変更
7. サイズ変更
8. 保存
9. 公開ページ確認
10. 再編集
11. Font Awesome Freeでも同様に実施
12. Material Symbolsでも同様に実施

#### 14.4 回帰テスト

- プラグイン無効化
- 再有効化
- コレクション無効化
- コレクション再有効化
- プラグイン更新
- WordPress本体更新
- テーマ変更

既存のアイコンブロックやWordPress標準コレクションに悪影響がないこと。

### 15. 更新とアンインストール

#### 15.1 アップデート

新しいアイコンライブラリに更新する際も、既存のアイコン識別子を原則変更しない。

削除・改名されたアイコンについては互換性を確認する。

使用済みアイコンを破壊する変更を行う場合、移行方法を検討し、READMEと変更履歴に記載する。

#### 15.2 アンインストール

通常のプラグイン無効化では設定を削除しない。

アンインストール時の設定削除方針を明示する。

投稿本文やブロック属性には一切手を加えない。

アンインストールするとアイコンが表示できなくなる可能性があることをREADMEに記載する。

必要ファイル：

- README.md
- LICENSE
- THIRD-PARTY-NOTICES.md
- CHANGELOG.md
- インストール手順
- ライブラリの対応状況
- 対応WordPressバージョン
- 対応PHPバージョン
- アイコン追加・更新手順
- ビルド手順
- テスト手順
- 既知の制限事項

GitHub Releaseで配布できるインストール用ZIPを生成する。

ZIPには本番実行に不要な依存パッケージ、テスト用ファイル、生成前の元データを含めない。

ライセンス上必要なファイルは省略しない。

GitHub Actionsでは以下の自動化を検討する。

- PHP構文チェック
- WordPress Coding Standards
- PHPUnit
- SVG検証
- ライセンスファイル検証
- ビルド
- ZIP生成

GitHubへの実際の公開・プッシュ・Release作成は、利用者の指示があるまで行わない。

### 18. 開発の実施順序

#### Phase 1：公式API検証

WordPress 7.1のAPIを確認する。

サンプルコレクションと少数のアイコンを登録し、標準アイコンライブラリに表示されることを実証する。

REST API、保存、公開ページの表示まで検証する。

#### Phase 2：SVG互換性検証

Feathericon、Font Awesome Free、Material Symbolsから代表的なSVGを取得する。

必要な変換手法を確立する。

変換前後の表示を比較する。

特にstroke主体のSVGの変換品質を確認する。

#### Phase 3：ライブラリ統合

ライブラリの配布条件とバージョンを確定する。

正式なSVGを取得・変換し、全対象アイコンを登録する。

重複・欠損・破損を検査する。

#### Phase 4：管理画面

コレクション有効・無効設定と状態表示を実装する。

#### Phase 5：自動テスト

単体テスト、REST APIテスト、エディター操作テスト、SVG視覚比較を実施する。

#### Phase 6：配布準備

ドキュメント、ライセンス、GitHub Actions、ZIP生成処理を整備する。

### 19. Codexへの作業指示

上記仕様に従って実装すること。

ただし、いきなりすべてのライブラリの組み込みを開始しない。

最初にWordPress 7.1の公式APIを検証し、標準アイコンライブラリの左側に独自コレクションが表示されることを確認する。

次にSVGの互換性と変換方法を検証する。

検証で仕様と実際の挙動が異なる場合は、憶測で実装を進めず、公式ドキュメントおよびWordPressコアのソースを調査する。

確認する一次資料：

https://make.wordpress.org/core/2026/07/24/registering-and-rendering-svg-icons-in-wordpress-7-1/

https://developer.wordpress.org/reference/functions/wp_register_icon_collection/

https://developer.wordpress.org/reference/functions/wp_register_icon/

https://github.com/feathericon/feathericon

https://github.com/FortAwesome/Font-Awesome

https://github.com/google/material-design-icons

各フェーズでは以下を報告する。

1. 実装した内容
2. 実装ファイル
3. 実施した検証
4. 検証結果
5. 公式仕様との差異
6. 判明した問題
7. 未解決事項
8. 次フェーズで行う作業

検証した事実と未検証の推測を明確に区別する。

ライブラリやSVGの仕様が想定と異なる場合は、その差異を記録する。
